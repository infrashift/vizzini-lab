# Generated files and forked code must stay in sync

The docs name several places where checked-in files are produced from another source. A reviewer should expect the source and the regenerated output to change together, and should be wary of hand edits to the output.

## Generated outputs

- **`feature/buildfeatures/`**: the `feature_<name>_enabled.go` / `feature_<name>_disabled.go` pairs are generated from `feature/featuretags/featuretags.go` by `./tool/go generate ./feature/buildfeatures` (or `make generate`).
- **`depaware.txt` files**: regenerated when the dependency graph changes, and the diff must be part of the same PR (see the dependency footprint concept).
- **`tsnet/README.md`**: its first line says it is "auto-generated by misc/genreadme; DO NOT EDIT."
- **Kubernetes operator manifests**: the Helm chart templates in `cmd/k8s-operator/deploy/chart` are also used to generate the static manifest `cmd/k8s-operator/deploy/manifests/operator.yaml`. The docs say "developers must ensure that any changes applied to the chart have been propagated to the static manifest by running `go generate tailscale.com/cmd/k8s-operator`."

## Forked code under tempfork

- **`tempfork/acme`** is a vendored copy of Tailscale's fork of `golang.org/x/crypto/acme`. The fork exists in a separate repo so it can be rebased from upstream easily; `tempfork/acme` is then updated "in the same commit" that updates the dependency on that fork. A test (`TestSyncedToUpstream`) is meant to catch a forgotten update.
- **`tempfork/sshtest/ssh`** is a copy of `golang.org/x/crypto/ssh` changed to add test-only behaviors for testing Tailscale SSH, behaviors "that aren't necessarily desirable to have upstream." It is for tests, not production code.

## Git hooks and tool binaries

- Shared hook logic lives in the `githook/` package under `misc/git_hook/` and is also imported by another Tailscale repo. Changes under `githook/` or to `git-hook.go` require bumping `githook/HOOK_VERSION` so installed hooks rebuild.
- `tool/go.exe` is a small checked-in Windows binary whose source is in `tool/goexe`. It lets `./tool/go` run the correct, hermetic Go toolchain on Windows. The docs say the project always requires the latest Go release.
