# Tests required with every code change

`CONTRIBUTING.md` treats any change that alters code (as opposed to only documentation) as either adding functionality or fixing broken functionality. "In both of these cases, the pull request should include one or more tests to ensure that Tokio does not regress in the future." The pull request template repeats it: "Bug fixes and new features should include tests."

**Which kind of test**

There are two accepted ways to write tests: integration tests and documentation tests. "Tokio avoids unit tests as much as possible." A reviewer should prefer seeing new coverage in a crate's `tests/` directory or in doc examples rather than in `#[cfg(test)]` modules inside the source.

**Integration tests**

- They "go in the same crate as the code they are testing."
- "Each sub crate should have a `dev-dependency` on `tokio` itself," so all Tokio utilities are available in tests whatever crate is being tested.
- "The best strategy for writing a new integration test is to look at existing integration tests in the crate and follow the style."

**Special test crates**

- `tests-build/` "tests the various combination of feature flags" and is a separate crate "to work around limitations with cargo features". It is run with `cargo test --features full` and `cargo test --features rt`. Expected compiler output can be regenerated by passing `TRYBUILD=overwrite` to the failing command; check that regenerated output matches the intended change.
- `tests-integration/` holds tests "that require additional components than just the `tokio` crate".

**Running tests**

Because Tokio uses features extensively, common commands need `--all-features` (`cargo test --all-features`). Tests guarded by a `cfg` need that flag passed through `RUSTFLAGS`; for example a test marked with `tokio_unstable` is run with `RUSTFLAGS="--cfg tokio_unstable" cargo test -p tokio --all-features --test rt_metrics`. To run tests in a particular file, first check what its `#![cfg]` declaration requires.
