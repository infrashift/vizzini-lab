# Backend implementation conventions

Rclone maintains many backends, and CONTRIBUTING.md says that "keeping them as similar as possible to each other is a high priority". The "Guidelines for a speedy merge" and AGENTS.md set these rules.

## File layout

- Each backend is a single Go package, for example `backend/s3/`. The main implementation goes in **one file** named after the backend (`s3.go`). **Do not** split it into `fs.go` and `object.go`. A few existing backends do that, and the docs say not to follow them.
- API type definitions go in a separate file, by preference `api/types.go`.
- The test file (`remote_test.go`) uses `fstests.Run()` from `fstest/fstests`.
- Register the backend with a blank import in `backend/all/all.go`.
- Start from a similar backend and follow it exactly: "use the same code order, function names, layout, structure. **Don't** move stuff around and **Don't** delete the comments." `box` is the suggested template for directory-based remotes (it shows the directory cache), and `b2` is the template for bucket-based remotes.

## Shared libraries to use

- REST-style backends that parse JSON or XML should use `lib/rest`. If the provider has a really good Go SDK, use that instead.
- HTTP backends should use the Client or Transport from `fs/fshttp`. This gives them `--dump bodies`, `--tpslimit` and `--user-agent` support without any extra code. A backend that builds its own `http.Client` loses these features.
- Use `lib/dircache` for remotes that address directories by ID, `lib/oauthutil` for OAuth, and `lib/pacer` for rate limiting and retries with backoff.
- Use `lib/encoder` so that any path name can be encoded. Work out which encodings the remote needs with `rclone test info`.

## Capabilities

Implement as many optional methods as possible, because this makes the remote more usable (see the optional-features concept). Backend option documentation lives in the `Help:` fields of the Go options struct, not in markdown.

## S3 providers

A new S3-compatible provider is added mainly as a YAML file in `backend/s3/provider/`, using the tags of the `Provider` struct in `backend/s3/providers.go`. Provider differences are expressed as `Quirks`. Most quirks are `*bool` so that they can be true, false or "don't care", and they are adjusted until the integration tests pass. The README says not to run `make backenddocs` for this and not to edit the autogenerated parts of `s3.md`.
