# Backward compatibility and minimal changes

## Backwards compatibility

AGENTS.md: "**We take backwards compatibility very seriously.** PRs should not change the observable behaviour of existing commands, flags or rc API without very good reason." The public surface is therefore:

- command behaviour and output,
- command-line flags and backend options, including their names and defaults,
- the remote control (rc) API, which librclone also uses through `RcloneRPC`.

The Go API is treated differently: "Rclone does not try to preserve a stable Go API but try not to change it gratuitously." A reviewer should question a Go API change that has no clear purpose, but should treat any change to user-visible behaviour as a much bigger issue.

Compatibility also means not breaking existing installations. Rclone runs against many backends, "compatibility is key", and the backend integration tests are what guarantee it. Changes "should consider both known and unknown backends and should take care not to break functionality of existing installations". The librclone C interface is marked experimental and "may change in the future", so it is the one documented exception.

## Minimal, focused changes

AGENTS.md: "**Changes should be kept to the minimum.** Work hard to make the most elegant, smallest change you can. Do not refactor or re-order code unless necessary as this makes review more challenging." Contributors should re-use existing test scaffolding and existing library routines, for example in `lib`, rather than writing new helpers. For backends, CONTRIBUTING.md adds: don't move code around and don't delete comments.

Things to flag in review:

- unrelated reformatting, reordering or renaming mixed into a fix,
- new helpers that duplicate something in `lib/` or `fs/`,
- a fix placed in `fs/` or `vfs/` as a special case for one backend; it belongs in that backend, or behind a new Feature flag.

## Scope and process

The PR template says that anything beyond a trivial fix (typo, doc tweak, small obvious bug fix) should be discussed and agreed in an issue first, and that larger PRs which skip this may be closed. CONTRIBUTING.md requires new features to come with unit tests and documentation.

## AI-assisted contributions

The same standard applies whether or not a tool was used. The submitter must understand every line and must have run `go build` and `make quicktest`. Pull requests that "invent APIs that do not exist", do not compile, or do not do what they claim are likely to be closed. Verbose comments generated by AI tools should be cut down to the house style.
